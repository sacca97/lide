# 0007 — The LSP client is ours

- Status: accepted (not yet implemented)
- Date: 2026-11-24

## Context

The editor has to talk to language servers: diagnostics, completion, hover,
go to definition and references, rename, formatting and code actions.

## Decision

Write the client, over `lsp-types` or over a maintained fork of it.

## Why

There is no maintained, permissively licensed Rust LSP *client*:

* Zed's `lsp` crate is GPL-3.0-or-later and unpublished, and it depends on a
  fork of `lsp-types` that is also unpublished.
* The crates.io `lsp-types` (0.97.0) was last published in June 2024 and is
  behind the protocol.

The protocol types are not the hard part; the hard part is the lifecycle —
starting a server, tracking its capabilities, routing requests to the
document that owns a position, and mapping its diagnostics onto the editor's
locations — and that part has to be written either way.

## Consequences

* The client is a crate of its own (`lide-lsp`) with no UI dependency: it
  speaks the protocol and reports positions, and the editor decides what to
  draw.
* The protocol types come from `lsp-types`, pinned. If it falls too far
  behind, a fork of it is vendored the way Rune vendors `winit` — documented
  in the ADR at the time.
* Servers are started per project, configured in the project's settings, and
  shut down when the project closes. A server that crashes is reported and
  restarted at most once per document; it never takes the editor with it.
* This is the largest single piece of work left before Phase 2 can finish.
